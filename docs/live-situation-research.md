# 局势装备与技能推荐调研和实现方案

调研日期：2026 年 10 月 6 日。适用范围：国服端游、召唤师峡谷匹配、三人开黑。以下是开发方案，尚未实现到运行代码中。

建议把这项功能做成“保留选人时的玩法，再比较本次回城的几种选择”。助手需要说明当前证据、可以买什么、改变路线会牺牲什么。单纯增加敌方 AD/AP 数量阈值，或者把装备胜率换成一个 AI 分数，都不足以解决这个问题。

[Winrate 的技术文章](https://en.winrate.gg/articles/item-recommender)发表于 2026 年 2 月 27 日，提供了更具体的方法：作者先尝试预测胜负，发现模型几乎忽略装备特征，后来改成在同一局面下比较装备 A 和 B。线上先按英雄、位置和购买顺序筛候选，再进行两两排序。训练状态取自购买之前。作者也承认版本延迟、冷门装备样本不足和相关性限制。

这支持“候选池加局势比较”的设计，但不能据此宣称装备能提高多少胜率。文章使用的实际伤害占比等历史特征，也不等于本机接口能实时提供的字段；训练与运行时必须使用一致的输入。

固定提交：[88b8b8bb](https://github.com/NexusHero/LOLRecommender/tree/88b8b8bb6070a531d578777ddb13ba2b5828b10e)，提交日期 2026 年 6 月 24 日，MIT。

- [事件检测器](https://github.com/NexusHero/LOLRecommender/blob/88b8b8bb6070a531d578777ddb13ba2b5828b10e/core/src/eventDetector.ts)识别敌方购买、升级、死亡等事件，但[推荐引擎](https://github.com/NexusHero/LOLRecommender/blob/88b8b8bb6070a531d578777ddb13ba2b5828b10e/core/src/recommendationEngine.ts)只在开局、自己死亡或手动请求时调用模型。检测到购买不等于立即重算。
- [提示词构造](https://github.com/NexusHero/LOLRecommender/blob/88b8b8bb6070a531d578777ddb13ba2b5828b10e/core/src/llmProvider.ts)传入自己的装备，却没有传入敌方装备明细；[缓存键](https://github.com/NexusHero/LOLRecommender/blob/88b8b8bb6070a531d578777ddb13ba2b5828b10e/core/src/cacheService.ts)也没有敌方装备。不能直接满足我们的实时装备变化场景。
- [提供商实现](https://github.com/NexusHero/LOLRecommender/blob/88b8b8bb6070a531d578777ddb13ba2b5828b10e/core/src/providers/openaiProvider.ts)会把构造的局势提示发送给外部模型。它不符合本项目无上传、离线可用的约束。
- 提示词仍列举已移除的装备，也有装备 ID 与名称不对应的示例；仅检查返回 ID 是否存在，无法保证理由、名称和机制正确。

可以借鉴事件检测和结构化短理由；不能照搬它的数据流、缓存失效条件或提示词知识。

## 论文的方法和适用范围

[Field aware Factorization Machines for Item Recommendation in Multiplayer Online Battle Arena Games](https://d2j16w31g89z0j.cloudfront.net/site/ictc2025/abs/P05-24.pdf)是 ICTC 2025 会议论文，DOI 为 10.1109/ICTC66702.2025.11389113。全文四页，使用 15.15 版本的 12,074 场高分段单排，提取购买事件，以英雄、位置、已有装备、双方阵容和候选装备为不同字段学习交互。训练比较真实购买与抽样备选，评测使用完整装备候选集和排序指标。

它对“下一次购买”比最终装备集合更贴题，但评测仍是预测玩家买了什么。论文没有证明实时推荐改善胜率，也没有完整交代按对局、时间或版本隔离的划分办法。借鉴候选比较和评测结构；15.15 装备结论不进入当前数据库。

[Robust Player Conditional Champion Ranking for League of Legends](https://arxiv.org/html/2605.18338v1)发表于 2026 年 5 月 18 日，是英雄选择预印本。它把强度、风格和熟练度分开解释，提出按时间留出评测及消融；实际案例只有一名玩家的 100 场记录，作者明确不声称改善胜率。可借鉴可分解解释和验证方案，不能作为局内装备或动态加点已经有效的证据。本项目也不引入其历史记录和熟练度数据流。

近期的直接装备论文与课程项目，多数学习玩家的历史选择。此次所读资料没有提供适用于当前国服匹配的、充分验证的动态技能加点模型，因此加点采用逐英雄复核的规则，比泛化出一个“AI 最优加点”标签更合适。

## 拟采用的实现

### 输入和玩法延续

继续使用本机的三个只读端点。自己的金币、装备、等级和技能等级可以参与购买和合法加点判断；双方公开装备、英雄、位置和战绩可以提供上下文。数据未知时保留未知，队伍或模式无法确认、英雄不匹配、数据过期时回到原方案。

不读取敌方真实金币、伤害统计、坐标或冷却，也不根据接口缺失补造这些值。官方建议按需读取 [Live Client Data API 的子端点](https://developer.riotgames.com/docs/lol#game-client-api_live-client-data-api)。其数据可用性必须在国服实测，不能用其他产品展示的指标反推本机也能读取。

从选人延续英雄、位置、开黑成员、组合配置和玩法。例如娱乐 AP 路线不能因为常规 ADC 出装热门，就自动切回暴击路线。对线对象允许手动修正；当前主要威胁允许用户指定。手动位置继续保留，也不替代客户端的正式分路或任务信息。

### 装备候选和比较

处理顺序为：确认版本与模式 → 恢复当前玩法 → 生成候选 → 检查购买是否合法 → 计算组件和剩余价格 → 比较局势用途与核心代价 → 生成对应理由。

每个英雄玩法维护核心路线、可变选择和允许插入的小件。候选来自已复核的英雄方案、组合专用配置和局势机制库；不遍历所有装备后仅凭标签拼一套，也不为了凑数量补入被过滤的装备。

比较因素如下，具体权重需通过场景评审确定，不能随意当成胜率或概率：

| 因素 | 要回答的问题 |
| --- | --- |
| 当前玩法 | 这件装备支持所选连招、符文和组合分工吗？是否破坏必要核心？ |
| 当前对象 | 对线时主要面对谁？团战时必须打谁或防谁？对象未确认就降低建议力度。 |
| 机制适用 | 防的是普攻、爆发、持续伤害还是特定控制？功能效果能由这个英雄有效施加吗？ |
| 本次购买 | 金币够完成什么？已有组件是否能合成？买后是否有格子？ |
| 后续代价 | 是否推迟关键成装、攻速或其他已复核的发力条件？是否需要过早启动叠层？ |
| 队伍分工 | 是否已有能覆盖当前目标的重伤或保护手段？公开装备不足以确认覆盖时需说明。 |
| 证据范围 | 是用户明确确认、已展示装备事实，还是英雄机制推断？不显示未经校准的百分比信心。 |

常规回城呈现最多三个有不同用途的选择：继续核心、解决当前压力、兼顾功能。证据不足时可以只保留原路线。每个选择同时给出现在能买的组件、目标成装和相对于原路线的取舍；无须用户阅读长攻略。

例如，“某目标展示了魔抗装”只能支持考虑法穿，不能支持“你打不动就是因为魔抗”。法穿是否提前，应继续检查是否常打这个目标、当前核心能否完成以及所选玩法的输出方式。治疗、护盾和控制同样需要逐机制核对，不使用“有治疗英雄就全队买重伤”的泛化规则。

### 理由和更新时机

理由由同一份决策记录生成，包括观察事实、触发条件、选择用途、替代选择和代价。不能先推荐一件装备，再拼接与评分无关的好听说明。

示例格式：“你确认现在主要受到该英雄的普攻压力；本次可以完成防御鞋。它更适合应对普攻，但会推迟当前路线的输出成装。若准备避战发育，可继续核心组件。”这是展示结构的示例，具体英雄与装备仍需规则核实。

读取可以持续进行，排序只在购买、卖出、预算跨过可购买门槛、玩法或关注对象改变、版本资料改变时更新。不要每次轮询都洗牌；轻微变化保留原顺序，关键变化写明原因。缓存必须覆盖实际参与判断的敌方装备和玩法等字段。

用户已经选择的回城目标保持优先。出现新压力时展示备选和变化原因，不能反复把用户目标改回自动推荐。游戏切换、连接失效和手动修改都要有独立的状态边界。

### 技能加点

技能加点单独维护，按照英雄、位置和所选玩法检查当前技能等级、等级门槛和特殊机制。已投入的技能点不可撤回，因此改变优先级前必须比较后续损失。

第一阶段采用已复核的默认顺序和少量有明确机制依据的分支。保护型辅助、对线型辅助和组合专用玩法不能共用一句“控制多就主护盾”。建议必须解释升级具体改变什么，以及会减少哪一项能力的成长。缺少可靠分支时继续原顺序。

对厄斐琉斯、乌迪尔、变身英雄等，未经独立核实的加点规则继续明确标为暂不支持动态判断。上路等级超过十八时，不能简单按等级减技能等级总和生成额外可用点，也不能提高技能最大等级来凑数。

### 数据库更新

游戏静态数据、机制规则、英雄玩法和组合配置分别记录版本及复核日期。每条可触发的规则至少包含适用模式、英雄或玩法、观察条件、候选、否决条件、理由、代价、来源和已验证版本。

更新流程是先下载或导入到待核对区，对比装备删除、合成、价格、被动、英雄技能和模式改动，再定位受影响规则。通过校验和场景评审后替换本地资料；保留上一份可用资料以便回退。只改版本字符串不能使旧规则变成“最新”。

社区投稿首先是待核实线索。预览资料不能覆盖正式服规则，当前大乱斗资料不能覆盖峡谷规则，全球服上线日期不能直接当国服实际版本。过期或未复核的自动规则停止触发，参考资料仍可保留并明确状态。

本项目保持无账号、无历史记录、无对局上传，采用本地规则和数据运行。若未来试验学习排序模型，应使用来源与用途明确的公开数据，离线训练，并先与简单基线比较；外部 LLM 不是当前功能的依赖。

## 实现次序和验收

1. **修正版本机制。** 首先处理蛇女鞋限制、真实槽位和任务状态、十八级以上状态以及模式识别；对未知状态保守判断。核对互斥装备、任务专用装备和英雄专用购买限制。
2. **重做下一次购买比较。** 引入逐英雄玩法候选、核心保护、组件用途和清晰取舍；已有手动目标与组合配置必须保持。
3. **扩大局势机制库。** 分别支持普攻压力、不同魔法伤害、穿透、治疗、护盾和具体控制。对线、团战及开黑成员分工进入解释。
4. **补齐技能和维护工具。** 技能分支逐英雄核实；维护工具列出受版本变更影响的条目和待复核来源，减少以后更新成本。

验收不能只检查输出存在。场景至少覆盖：同一英雄的不同娱乐玩法；有钱完成核心却出现一般防御信号；必须打的前排与可以绕过的前排；混合和真实伤害；技能治疗与装备吸血；队友重伤已覆盖与不能覆盖；合成腾格、任务鞋槽及任务未知；蛇女鞋；十八级以上及特殊加点；敌方换装后的缓存；数据过期；用户目标保持。

每个场景评审“候选是否合法、当前能否购买、是否破坏玩法、解释是否对应真实依据、缺数据时是否合理弃权”。有专业判断差异的场景保留多个选择。模拟接口和单人训练可以验证读取、购买同步及界面；敌方威胁排序还需真实对局或经人工复核的公开场景，不能靠一个人的训练房间证明。

如训练排序模型，应使用购买前的状态，按完整对局隔离训练与测试，并加入后续版本留出。归一化等处理只在训练集拟合；比赛最终胜负不作为实时输入。购买预测的 Hit@K 或 NDCG 与胜率改善分别表述，不能互相替代。

应用只展示多个可选建议，由玩家执行购买和加点，不加入游戏输入自动化或敌方冷却追踪。这个范围也与 Riot [保留玩家决策及提供多个选择的原则](https://developer.riotgames.com/docs/lol#game-integrity)一致；使用官方读取接口不等于产品已得到 Riot 审核或背书。
