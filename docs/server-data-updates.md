# 0.54 资料服务器更新

本阶段实现 B 服务器的定时采集、校验、候选保存、统计资料签名，以及客户端的后台下载和离线缓存。2026-10-15 已验证独立域名的公网 HTTPS 和客户端资料链路；0.54.0 安装包已同步发布到 GitHub、Gitee 和 A 的下载页。

## 更新哪些数据

| 数据 | 本阶段的更新计划 | 来源和边界 |
| --- | --- | --- |
| 五路排行榜 | 每天两次 | OP.GG 全球/韩国 × 黄金+/翡翠+/钻石+，共六份榜单；保留分路、样本数、胜率、选用率、禁用率、来源梯度及统计时间，不标成国服统计 |
| 常用配置 | 每天两次 | 首先覆盖全球翡翠+的常用位置：核心出装、后续装备、符文、召唤师技能和加点路线；其他筛选仍由现有客户端按需获取 |
| 海克斯大乱斗参考 | 每天两次，同补丁也重新检查 | OP.GG 的英雄出装及强化参考；当前解析器没有可靠的逐强化胜率，不能据此生成强化胜率排行榜 |
| 英雄强化选取记录 | 随上述任务检查，失败保留旧记录 | Mayhem:Meta 的同补丁逐英雄公开汇总，只保存强化 ID、选取场次和隐藏状态；零观察不作为禁用，榜单不作为完整资格池 |
| 英雄、装备、符文、召唤师技能、海克斯基础资料 | 每天两次检查版本及同版本内容 | Riot Data Dragon、腾讯中文名称和 CommunityDragon；包括同补丁的数值修正，不以版本号相同为由完全跳过 |
| 配合规则、攻略文字和组合设计 | 经维护者核对后更新 | 策划内容不能靠刷新网页自动证明正确，也不能冒充统计胜率 |

这里的海克斯是海克斯大乱斗（ARAM Mayhem / KIWI），不是云顶之弈，也不是斗魂竞技场。

英雄选取记录随既有 `hex-builds` 文件验签、校验与空闲启用，不新增计时器或无签名下载入口。服务器串行采集、限流和总预算不变；只允许 `mayhemmeta.com` 首页及带明确补丁的英雄页。该补充源失败会在 `status.datasets.hex-pools` 标记 `partial`，不阻断其他已验证资料发布。客户端按需刷新 OP.GG 配置时不会批量读取英雄池，也不会覆盖较新的池记录；资料卡单独显示实际采集时间，不把它当作统计截止时间。

采集前先核对首页明确列出的可用补丁；目标补丁尚不可用时只读取首页，跳过逐英雄请求并保留已有记录。页面未提供补丁索引时仍逐英雄严格核对，绝不将默认返回的旧补丁当成新版。

模式目录中的 `Enabled:false` 只表示客户端资料明确停用，不是完整的服务器英雄黑名单。图鉴把目录状态、英雄选取记录和获取途径分开。26.21 的 K/DA 额外强化、Command Line 升阶重随与任务解锁按版本核对；不从 `AugmentLevelData` 推断选择轮次，不把旧补丁的四次选择复制成新版完整池。尚无可靠自动接口确认本局主秀时，只提供明确标记的手动预览，新局清除。

## 腾讯国服独立来源（0.59.7）

保留当前 OP.GG 默认，新增“更多工具 → 各路排行 → 来源 → 腾讯国服”。网站为[腾讯101](https://101.qq.com/)，公开 JSON 位于 `https://mlol.qt.qq.com`；先用 `/go/database/versionlist?zone=lol&from=h5` 确认当前补丁，再读取 `/go/battle_info/odp_proxy/lol_101strategy`。使用网站对应的黄金+（24）、翡翠+（26）、钻石+（27）和五路记录；`lane=ALL` 必须大写。不因最新版本无数据而静默降级。

启用 `--national-rankings` 后，每轮原任务结束时额外读取三档段位，最多8请求、4 MB、2分钟，沿用1.5秒请求间隔和现有 systemd/flock，无新增服务器定时器。三档完整校验后，用既有固定 Ed25519 签名链发布 `/national/v1/latest.json`，保留单个当前文件；失败保留旧文件并报告非零状态。它与现有 OP.GG v1/v2清单独立，不能互相代替。客户端检查签名、补丁、已接受序号和逐段位来源日期；服务器渠道不可用时按需直读官方，绝不把较新的直读缓存降级为服务器旧数据。

单英雄配置按需读取同域 `lol_101strategy_build` 与 `lol_101strategy_runeinfo`，不在服务器批量抓取全部英雄；要求装备与完整符文日期一致，保存独立12小时缓存。核心装备是三件组合，不保证购买顺序；完整符文按数值名次排序，保留真实场次。排行和装备没有公开场次，保存为未知。未确认全区、队列与完整样本覆盖，不能宣称全区单双排总体；此来源仅供参考，不写客户端、不替换默认配置、不混入阵容评分或概率曲线。来源格式变化、限流或补丁缺失时明确提示，保留有效缓存。

## 采集与推荐算法的区别

采集任务负责读取来源、核对补丁/英雄/位置/地域/段位、解析和保存数据。它不重新训练 OP.GG 的算法，也不收集玩家战绩。

Riot 的 Data Dragon 提供静态资料，不能单靠它得出胜率排行；其资料更新时间也可能晚于游戏补丁。[Riot 文档](https://developer.riotgames.com/docs/lol#data-dragon)

OP.GG 的梯度是其自身多指标算法结果。软件保留来源给出的梯度与统计指标；开黑阵容契合度由本地推荐逻辑另行计算，不能把契合度百分数解释为获胜概率。[OP.GG 梯度说明](https://help.op.gg/hc/en-us/articles/31089225669017-champion-tier-calculation-explained)

OP.GG 没有向第三方提供稳定的数据 API 契约。其帮助说明要求数据来源署名、避免过量请求；页面及响应格式也可能变化，因此保留来源链接，限速访问，遇到 403/429 暂停本轮该来源，不绕过限制。[数据使用说明](https://help.op.gg/hc/en-us/articles/31091405109401-Can-I-use-OP-GG-data)

## 两台服务器保持独立

- A：房间中继、方案与投票转发、现有备用安装包下载。
- B：公开资料采集、候选保存和统计资料签名；通过独立的 `https://data.riftbuddy.dpdns.org` 提供资料。
- 客户端：本机 LCU 连接、玩家显式点击后的配置操作、离线资料和推荐计算。下载完成后遇到选人、对局或未知客户端阶段先暂存，回到大厅等空闲阶段再启用；短暂掉线不会解除已观察到的对局状态。

没有新增数据库、容器集群或常驻浏览器。任务运行完即退出；现有 t4g.small / 2 GiB 足以先承载此规模的定时任务，实际占用由 systemd 记录。

## 采集限制与失败处理

- 一次只下载一份响应，起始间隔至少 1.5 秒；整轮最多 1,000 次请求、512 MiB 响应数据、45 分钟网络采集。
- 来源固定为已配置的 HTTPS 域名，国服新增腾讯 `mlol.qt.qq.com`；禁止携带登录凭据或跟随重定向。OP.GG 网页和统计接口共享限流暂停状态。
- 单份 OP.GG 响应最多 4 MB；基础资料最多 64 MiB。连续三次服务错误或连接错误会暂停该来源。
- systemd 设 CPU 配额 40%、内存高水位 640 MiB、硬上限 768 MiB；进程堆上限 320 MiB，执行总超时 50 分钟。
- 同一补丁内也刷新统计。仅 `fetchedAt`、`checkedAt` 变化不会复制一套内容相同的数据。
- 某份统计失败时，保留该范围的有效旧资料；有明确来源版本的旧配置保留其真实补丁。不会用另一个地区的统计冒充。
- 新基础补丁缺少完整的六份榜单时，暂不替换既有完整候选。
- 压缩文件和原始内容都保存 SHA-256，读取时重新验证；四类文件通过校验后才切换 `current.json`。
- 候选只保留当前有效的一份。新候选完整校验并切换指针后，自动删除旧候选和遗留的采集中间目录；无内容变化的检查也会清理旧副本。更新期间允许新旧两份短暂共存，512 MiB 预算覆盖这段过程；达到上限时保留当前资料并报告。

SHA-256 用于检查内容完整性；它不等同于数字签名。只有完整成功的一轮才会进一步生成 Ed25519 签名清单；采集候选和公开的签名统计资料分开保存。

## 客户端如何更新

2026-10-19 已部署并验证 `/v2/latest.json`，提供基础资料、排行榜、常用配置和海克斯参考的签名整套资料。0.58.4 起先检查 v2；`/v1/patches/<补丁>/latest.json` 继续为旧客户端提供三类统计。未启用过有效 v2 资料的客户端在 v2 不可用时兼容 v1，已启用过 v2 后不再混入独立 v1 统计。本次公网验签、四份内容校验、选人期间暂存和离线重启验证使用隔离状态，无真实客户端或符文写入。

v2 清单用同一固定公钥验签，包含基础英雄/装备/符文资料及三类统计，四份内容全部验证后整体启用。采集开始时冻结预期英雄分路、六个榜单和全部海克斯英雄范围，缺项、旧解析器或补丁不符均拒绝发布。压缩文件使用 SHA-256 命名，单份限 8 MiB 压缩/16 MiB 解压，整套限 24/48 MiB。签名、哈希、版本或格式失败时保留当前整套资料。发布端先准备全部文件，再替换各协议清单；捕获提交失败时恢复原清单，不声称两个独立清单路径具备跨文件崩溃原子性。

主进程在软件启动后统一检查一次，持续运行期间每 12 小时自动检查；主窗口和侧栏不各自采集。用户可在“设置 → 游戏资料”关闭自动更新，或点击“检查更新”。失败仅显示状态，不弹出阻塞选人的窗口，也不会改动符文页或召唤师技能。

通过验证的三份文件和签名清单作为一代统计资料保存。已启用缓存 `data-feed.json` 与待启用缓存 `data-feed.pending.json` 分开验签、校验，下载不会覆盖正在使用的缓存。确认空闲后先准备完整统计引用，再同步提升缓存并切换引用；失败保留原资料。重启只直接恢复曾启用的 schema 2 缓存，待启用资料继续等待大厅等已确认的空闲状态，首次未连接也不视为空闲。旧 schema 1 缓存无法证明曾启用，保守迁移为待启用资料。玩家显式更新基础资料沿用原有阶段门禁。启用时保留比服务器更近的本机来源记录、地区和段位选择，不修改保存的阵容或个人配置。只收到检查状态时不会重绘选人页。

v2 已启用缓存为 `data-generation.json`，待启用缓存为 `data-generation.pending.json`。重启只恢复已启用的有效签名整套资料；待启用资料继续等待确认空闲。启用前准备引用、个人组合问题和图片来源，最后重新检查阶段及并发修改，一次发布到两个窗口。手动资料用实际文件哈希标识；同补丁内容不同时需点击“采用服务器资料”，该操作绑定当前候选，选人期间仍不可启用。个人组合及其复核锚点不因更新重写。

图片缓存按基础内容身份分开，来源 URL 相同才复用内置图片，旧同名缓存不会盖住新来源。独立技能精确数值和加点估算表仅在其内置基础内容一致时使用；不一致时回退并明确缺少精确来源，不把旧数值当作新版本。人工搭配规则与博主组合仍须单独有据复核，v2 不会自动发明或更新这些规则。

签名私钥为 B 上的 `/var/lib/rift-buddy-data/signing/ed25519.pem`，目录权限 0700、文件 0600，用户为 `riftdata`；它与 Windows 上的 SSH 登录私钥用途不同。公钥固定在 `services/data-feed.mjs`，密钥 ID 为 `data-20261014`。不要重新生成同名签名密钥来修复访问问题；换钥需要同步发布客户端信任的公钥。

公开目录为 `/srv/rift-buddy-data`，只保留 v2 当前整套清单及四份内容、v1 当前补丁清单及三份统计，预算为 256 MiB。密钥、采集日志、状态和原始候选不放入这个目录。文件全部保存后才替换各协议清单，重新核验当前文件后删除旧补丁目录和未引用的旧文件；未变化内容复用已有文件。完整采集、签名发布和清理在同一个 `flock` 下串行完成。

客户端下载时若恰逢更新、旧文件已被删除，收到 404/410 后会重新读取最新清单并重试一次；仍失败则继续使用本地有效资料。部分采集失败不替换公开版本，当前有效资料可以来自上次成功采集，但不额外保留历史副本。

## 目录与调度

固定连接方式见 [服务器运维文档](server-operations.md)。实际版本目录以本机 `.ssh/rift-buddy-servers.json` 和服务器 unit 为准。

| 路径 | 用途 |
| --- | --- |
| `/opt/rift-buddy-data/current` | 指向当前采集程序的版本目录 |
| `/opt/rift-buddy-data/current/data` | 发布时带入的有效基线，采集过程不修改它 |
| `/var/lib/rift-buddy-data/updates/current.json` | 当前完整候选的指针 |
| `/var/lib/rift-buddy-data/updates/releases/<版本>/` | 四份 `.json.gz` 及 `manifest.json` |
| `/var/lib/rift-buddy-data/updates/status.json` | 检查时间、内容变化、覆盖数量、错误及网络预算 |
| `/var/lib/rift-buddy-data/collect.lock` | `flock` 进程锁，防止并发维护覆盖候选 |
| `/srv/rift-buddy-data/v1/patches/<补丁>/latest.json` | 该补丁的签名统计清单；每次变化使用递增序号 |
| `/srv/rift-buddy-data/v1/assets/<SHA-256>.json.gz` | 不可变的统计文件，供客户端按需下载 |

沿用北京时间 **10:17、22:17** 的计时器，每轮附加最多 10 分钟随机延迟。停机后由 `Persistent=true` 补跑错过的任务。

status 中 `checkedAt` 表示本轮检查结束，`changedAt` 表示检测到该类内容变化，`lastCompleteAt` 只在这一类本轮全部检查成功时更新。还需结合整轮 `state` 和 `release` 判断内容是否成功保存为候选。

## 查看状态和手动刷新

在本机 PowerShell 执行：

```powershell
ssh rift-buddy-data 'systemctl status rift-buddy-data.timer --no-pager'
ssh rift-buddy-data 'systemctl show rift-buddy-data.service -p ActiveState -p Result -p ExecMainStatus -p MemoryCurrent -p CPUUsageNSec'
ssh rift-buddy-data 'sudo -n cat /var/lib/rift-buddy-data/updates/status.json'
ssh rift-buddy-data 'sudo -n journalctl -u rift-buddy-data.service --no-pager -n 30'
```

需要额外刷新时，只启动已有 service，复用它的权限、资源限制和锁：

```powershell
ssh rift-buddy-data 'sudo -n systemctl start --no-block rift-buddy-data.service'
```

退出码 0 表示整轮完整；2 表示有部分失败或限定范围测试，有效来源仍可能产生新候选；1 表示无法保存完整候选或运行错误。`inactive` 可以是正常完成，必须同时查看退出码和 status。不能仅因 timer 显示 active 就认定资料已更新。

采集服务的内存软／硬限额为 640／768 MiB，Node 堆上限仍为 320 MiB，为同补丁装备公式与字典解析留出进程内存。维护时结合 cgroup `memory.events` 的增量和整机可用内存判断节流，不能只凭单次累计计数解释全部耗时。在线调整须先保存有效 unit 和覆盖文件，核对 PID 不变、实际限额生效，再验证完整采集和签名发布；不要在占用高于旧硬限额时直接降低限额，也不要用广泛的 `systemctl revert` 清除其他覆盖。

测试使用虚拟响应和临时目录，不向真实客户端写入。维护者本地可执行：

```powershell
node --test tests/server-data-fetch.test.mjs tests/server-data-store.test.mjs tests/server-data-collector.test.mjs tests/data-feed.test.mjs
```

生产程序入口是 `scripts/collect-server-data.mjs`，unit 模板在 `deploy/data/rift-buddy-data.service`。部署时只打包入口的实际依赖和四份基线资料，核对哈希后放入新版本目录；临时备份旧 unit，再切换程序链接。验证新部署、定时器和签名资料成功后，删除被替换的程序目录、旧备份和上传归档；更新失败时先恢复当前服务，不删除它。自动资料清理只处理生成目录与文件，跳过符号链接和无法识别的维护文件。

### 人工社区资料快照

人工核验的组合与海克斯路线独立发布到 `/community/v1/latest.json`，沿用固定 Ed25519 公钥、压缩前后 SHA-256 和原子清单。它不属于每天两次的自动采集，采集器不能自动更新人工复核日期。目录仅允许 GET/HEAD；正文不含玩家数据。

