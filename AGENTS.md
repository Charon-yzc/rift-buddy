# 开黑搭子

Windows desktop app. Use the native Windows Node.js / pnpm runtime; WSL is unavailable.

- Electron main/preload live in `electron/`; UI in `src/`; shared recommendation logic in `src/core/`.
- Game data snapshots and images are bundled for offline use. Static data is not evidence of win rate or optimal builds. Label curated recommendations and stale rules honestly.
- Never log LCU, Riot Client or SGP credentials. LCU and Riot Client Basic credentials connect only to loopback. The user-authorized match-history module may query fixed HTTPS Riot/Tencent SGP hosts with the matching SGP token; never follow redirects or forward Basic credentials. Never read game memory or automate game inputs. Rune writes require an explicit in-app user click. Replace one editable rune page, preferring the last written page, then the current page; create only when no editable page exists. Never modify read-only preset pages. Automated tests must mock rune writes.
- Preserve manually configured positions during client sync. Never invent enemy champions, bans, or hidden player data.
- The user authorized League Akari match-history migration on 2026-10-17. Keep personal match history in bounded memory on this computer; never upload it to project servers, relay rooms, telemetry or backups. On 2026-10-20 the user explicitly authorized sharing only one's own bounded anonymous hero-count summary and preference mass with the joined room; rebuild that narrow payload, keep member ownership, and never include raw games, player identifiers, notes or credentials. Replay downloads/watch requests require an explicit in-app click; tests must mock them. No app accounts, subscriptions or telemetry. On 2026-10-22 the user authorized explicit feedback uploads consisting only of user-entered text, user-selected re-encoded screenshots and app version, with server quotas and seven-day retention. Never attach logs, settings, credentials, raw matches or account identifiers automatically.
- On 2026-10-20 the user authorized persisting only their bounded hero-count summaries locally, separated by a hashed account/region key, including explicitly imported own statistics. Keep raw matches in memory only; exclude the summary cache from settings exports and installers.
- Validate with `pnpm test`, `pnpm check`, then a packaged-app smoke test. Preserve user files and do not publish without explicit authorization.
- Phase delivery defaults to pushing and merging code. Build, verify and keep installers locally; upload release binaries only when the user explicitly requests them or for a major update. Keep README downloads linked to an already published package and distinguish it from the current source version.
- Whenever an installer is published, publish the same version and installer bytes to both GitHub Releases and the Gitee mirror at `https://gitee.com/legender134/rift-buddy`. Generate bounded Gitee parts with `scripts/package-gitee-mirror.mjs`, upload the mirror manifest last, and verify both download channels and SHA-256. Never mark the Gitee mirror synchronized before its assets are available; retain historical releases.

## Server access and responsibilities

- This project has two existing AWS ARM servers. Use native Windows OpenSSH and the persistent aliases below; a new session does not need earlier chat history. Read [the server operations guide](docs/server-operations.md) before remote maintenance.
- Connection settings and private keys live outside the repository in `%USERPROFILE%\.ssh\`. `%USERPROFILE%\.ssh\config` is the authority for addresses, users, keys and jump hosts; `rift-buddy-servers.json` records expected instance identities, roles and verified deployment locations. Read this local inventory before changing a server; verify its instance identity when starting maintenance.

| SSH alias | Responsibility | Current services |
| --- | --- | --- |
| `rift-buddy-relay` | A: player-facing room relay, HTTPS/WSS and fallback installer downloads. Keep bulk data collection off this host. | `relay`, `caddy`, `rift-buddy-relay-health.timer`, `rift-buddy-feedback` |
| `rift-buddy-data` | B: collect and validate public game data; retain only the current valid candidate and signed feed. Connect directly from the maintenance computer. | `rift-buddy-data.service`, `rift-buddy-data.timer`, `caddy.service` |

- Existing `rift-buddy` / `free-vps` aliases remain compatible with A. Start with read-only checks: `ssh rift-buddy-relay 'systemctl is-active relay caddy rift-buddy-relay-health.timer'` and `ssh rift-buddy-data 'systemctl is-active caddy rift-buddy-data.timer'`.
- Both hosts have independent SSH connections and runtime responsibilities; do not restore a dependency on A as B's jump host. B's SSH source is restricted to the verified maintenance computer's public IPv4 `/32`, recorded in the local inventory. If that address changes, verify the new source and update B's rule through the authorized AWS console; do not open SSH to every address.
- Keep private keys on the Windows host. Do not copy them to either server, Git, installers or tickets; do not forward the SSH agent. Keep strict host-key checking enabled. Missing credentials or changed host identity must be resolved using the verified instance, never by disabling verification or guessing old addresses.
- Reuse authorization for the current maintenance task. Inspect active systemd configuration, back up affected files, apply the smallest change, and verify service/data health afterward. Existing access is not authorization to buy or recreate instances, change billing/security exposure, or delete unrelated resources.
- Server retention: after validating and activating a replacement, remove superseded project deployments, candidate snapshots, public data assets, installer copies, upload archives and temporary deployment backups. During replacement retain the active version until the new version passes validation; on failure keep the active data. Preserve active runtimes, credentials, certificates, required state and bounded operational logs. Delete only verified project-generated targets, never unrelated files or symlink destinations. GitHub/Gitee release history and local user files are outside this server cleanup policy.
- B collects base game data, six ranking scopes, default-source builds and Hex references, then signs the three statistical datasets after a complete round; see [data update operations](docs/server-data-updates.md). Use the existing systemd service and its process lock for collection and publishing. Candidates and status are under `/var/lib/rift-buddy-data/updates/`, signed public files under `/srv/rift-buddy-data/`; keep signing material outside the public directory. Public HTTPS at `https://data.riftbuddy.dpdns.org` and the pinned-signature/download/cache/deferred-activation flow were verified on 2026-10-15 using isolated client state; desktop installer 0.54.0 is published on GitHub, Gitee and the relay download site with matching original installer SHA-256. Client feed code must verify the pinned signing key, retain offline data and defer activation during drafts/games. Announcements and server-owned room codes/snapshots remain future work. Explicit text/image feedback uses an isolated private bounded service on A; preserve its seven-day retention and never expose a public read endpoint. Client LCU access and explicit player actions stay local.
